# Kenxu 逐连接实际计量改造设计

状态：**设计与离线契约验证完成；核心改造、真实流量试点和生产部署尚未完成。**
日期：2026-10-15。当前生产继续使用原 Xray 用户累计计数；本文件不是安装指令，也不将现有网站关联值改名为准确字节。

## 1. 要解决什么

管理端需要回答“该用户的大部分代理字节到了哪些目标”，而不是“某网站出现的那一分钟总共有多少字节”。准确性包括两个独立问题：总计是否正确，以及实际字节是否分到了正确的用户、逻辑线路、目标和时间段。两者都要用独立已知字节的测试确认，不能因为分类合计等于原总计就断言总计正确。

计量范围是受管代理连接在统一转发点观察到的上下行字节，含目标自身的 TLS／HTTP 等字节，不是文件净大小、网卡包量或 Azure 账单。域名只是目标标识；共享 CDN、IP 直连和连接复用不一定能确定某个“网站”或应用，不能把所有 OpenAI 域名访问都断定为 Codex。未知部分必须保留。

## 3. 最小架构

```text
已认证的 VLESS / Vision / XUDP 逻辑连接
  → 原生转发计数路径上的 per-flow 字节观测
  → 仅本机可访问的快照与关闭事件确认接口
  → 采集器独立 SQLite 耐久队列（先落盘、后 ACK）
  → 门户独立 flow-report 入口（原用户计量报告继续工作）
  → 用户＋逻辑线路＋分钟＋目标的准确分类 / 未知 / 核对差额
```

### 核心内必须保留的信息

`core_epoch + flow_id` 是连接身份；另含受管 `email`、来源 IP、目标主机／IP、端口、TCP／UDP、已选出站标识、开始／最近活动／结束时间、上下行累计实际字节、观测完整性。逻辑线路由门户根据该 agent 的已注册 email 映射，不相信采集器自报的其他 user_id；SG2 和 UK 使用不同 email，UK 仍只由 SG2 的一个 agent 上报。

只跟踪受管身份，不存 UUID、URL 路径、正文或 TLS 明文。连接目标在可确定时绑定一次；不能在累计若干字节之后把整个连接从一个目标改名给另一个目标。不知道目标时记入 unknown，不反查 CDN IP 猜网站。Mihomo 客户端传来的域名可使用；必要的已有 SNI 信息只能作为有来源标记的目标提示，不新增 TLS 解密。

### 接入计数路径，而非再包一层盲目计数

固定版本的关键位置：[dispatcher.getLink / WrapLink / routedDispatch](https://github.com/XTLS/Xray-core/blob/d2758a023cd7f4174a5a5fa4ff66e487d4342ba0/app/dispatcher/default.go)、[SizeStatWriter](https://github.com/XTLS/Xray-core/blob/d2758a023cd7f4174a5a5fa4ff66e487d4342ba0/app/dispatcher/stats.go)、[Vision / CopyRawConnIfExist](https://github.com/XTLS/Xray-core/blob/d2758a023cd7f4174a5a5fa4ff66e487d4342ba0/proxy/proxy.go)。

拟复用 Counter 接口，将既有实际计数点与连接计数关联；保留 SizeStatWriter 等具体类型，不能用任意包装器破坏原生快路径类型判断。一个已转发字节只经过一个连接分类计数点。Dispatch 与 DispatchLink 都要覆盖；MUX 只对拆分后的逻辑流计目标，不能同时计外层承载和子流；XUDP 需要自己的会话身份与终结处理。错误／拒绝的流量口径必须在测试中确定，不能把“客户端已成功收到文件”当成所有代理字节的定义。

**快路径门槛：** 当前源码的 Linux splice 分支在 `TCPConn.ReadFrom` 返回后才 `Counter.Add(w)`，所以连接未结束时，15 秒轮询不保证这些字节已经进入计数。这是源码证据支持的时序风险，不是 hdc 异常流量的已验证根因；仍需复现。试点可以只对隔离测试流禁用 splice，先验证逐块实时计数，不能全站偷偷关闭优化。若保留 splice，必须实现并验证有进度检查点的同口径计数；否则不得宣称“长连接实时准确”。

上游 [#5446](https://github.com/XTLS/Xray-core/issues/5446) 报告了特定无 flow 情形的重复计数；它不是当前 Vision 配置中发生同一问题的证明。必须分别测试当前原版和候选版本，不能先对历史数据统一除以 2。

### 快照、短连接与可靠性

- 启动／关闭事件只作生命周期提示，累计快照才是补报依据。短于采样周期的已关闭连接也必须保留最终字节，直到采集器落盘 ACK，不能只轮询活跃连接。
- per-flow 累计值不清零；进程 epoch、严格递增序号与不可变身份用于去重。重复相同报告只确认，冲突报告隔离；已有 epoch 里的单个计数回退不能像新进程一样从零重新入账。
- 持久队列与确认游标同一事务；SIGTERM 时取最终快照并排空。原生用户计量与 flow 入口分开，flow 异常不能卡住所有旧计数补报。原总账与新 flow 统计不能叠加收取同一字节。
- 已关闭流 ACK 后可压缩为分钟／目标聚合及不带 IP／域名的去重标记；压缩前后字节守恒。ACK 前不得因显示只取 Top 10、事件订阅者过慢或队列轮换丢失字节。
- 访问元数据与重试队列字段仍限 30 天；超期只脱敏目标／IP，保留字节和必要幂等标记。快照与存储容量有上限，超限／断连／进程硬崩溃须标记覆盖缺口和未知量，不能声称任意断电也零丢失。
- 基于同一计数口径，在同一一致快照中检查 `分类字节 + unknown == 总字节`，独立校验负责发现共同的重复计数。并发读取的两个不同时间点不直接相减得结论；用户／方向分别校验，差额不能按比例强行抹平。
- 时间在计数发生时确定，按 UTC 分钟保存、按北京时间展示；不能把数小时长连接的全部用量记在关闭那一分钟。跨月、时钟跳变和关机最后一段都有专项测试。

## 4. my-ansible 的落地范围

本轮加入的 [只读预检](../kenxu_flow_preflight.yml) 和 [离线契约模型](../tools/flow_contract.py) 都不启用 flow 采集、不替换核心。模型用完整小型累计快照验证重试、短连接终值、epoch、身份和未知量守恒；不包含实际抓取、生产存储、ACK 压缩、并发快照或时钟，不能把模型测试通过当作 Xray 插桩完成。

未来实现建议增加固定 SHA／补丁哈希／构建哈希的核心产物，沿用现有 agent 注册；在独立 `kenxu_flow_shadow.yml` 中默认 `kenxu_flow_enabled=false`、`shadow_only=true`，显式指定一台 host 后才部署。不能借这次功能使用远程 latest 安装脚本或重建节点。产物需要 amd64／arm64 构建、上游 MPL-2.0 与借鉴源码许可校验；当前基线 Go 模块要求 1.26。

配置、服务、核心二进制、既有 agent queue 和用户身份都须有可回退版本。正式切换前排空原计数，失败恢复核心和业务配置，但不能拿旧数据库覆盖新字节。默认 SSH 用户／API 回环隔离、现有防火墙、Reality 设置、WARP、SG2→UK 和所有订阅凭据保持不变；JP／China 不计量直连仍明确不覆盖。

## 5. 分阶段验收

1. **当前原版校准**：两名虚构用户、两个本地目标，分别上传／下载已知原始 TCP 字节；另做 TLS 1.3 Origin，以独立底层 socket 计数核对，区分 TLS 开销。原版若有重复计数，先定位，禁止拿它当新方案的唯一正确答案。
2. **隔离 US2 影子试验**：与原核心并存，另用回环／Tailscale 可达测试端口、虚构凭据和临时门户库；不切换现用订阅，不开放公共 API。验证 TCP、Reality＋Vision、长 WebSocket、短连接、XUDP、MUX、断网重试、重启、跨月、容量上限。先测试，再单独批准真实账号试点。
3. **通过条件**：固定原始 TCP fixture 方向与字节必须完全一致且互不串号；TLS 按独立 socket 口径比较，不要求等于文件净大小。所有已知流＋unknown 与同一快照总量严格一致；零差额之外还要独立校验。1 万短连接在采集暂停后恢复仍有最终字节；长连接传输时不能等关闭才更新。SIGKILL 明确记录可丢失窗口，不伪造测试通过。
4. **性能门槛（待测目标）**：同硬件／相同流量下 p95 额外建链不超过 5 ms，吞吐下降不超过 10%，CPU 增量不超过 15%，稳态附加内存不超过 64 MiB。任一失败不全站推广；这些是目标，不是已测成绩。
5. **真实小范围试点**：只让 hdc 在一个获批节点使用，至少覆盖持续连接与高并发的实际场景；影子结果暂不改总账。出现不明差额、原订阅变化或 UK 路由回归即停止推广。
6. **逐台推广**：US2 → US1 → SG1／SG3 → 最后 SG2＋UK。每台先核对身份与路由、排空旧计数、原子切换、验证、再继续。用户界面只在该节点完成验收后显示“连接实际字节”；未切换节点继续显示关联口径。
