# 2026-10-25 新主机与部署仓库复核

## 部署范围

新增一台 Ubuntu 24.04 amd64 主机，以一套固定 Xray 核心和一个物理采集器承载两条逻辑线路：普通美国出口提供给现有授权账号；住宅 IPv6 出口只提供给指定的个人账号。每条线路使用独立的受管身份和出站标签，日志与字节不会因共享机器而合并为同一逻辑线路。

截至本次验收，受管范围为六台物理核心、八条逻辑线路；SG2 与 UK 仍共享原来的物理采集器。JP 已取消，历史记录保留；既有外部隐藏备用继续按其原来的未计量口径处理。

住宅 IPv6 由服务商客户端管理租约，固定槽位的独立源路由和 SNAT 绑定避免随普通出口漂移；不进入公共负载均衡。该出站只处理 IPv6 目的地，IPv4-only 目的地使用普通线路。验证租约缺失时拒绝住宅连接、普通线路不受影响，恢复后重用指定出口。

新主机仍需要单独的系统和路由审查，不能直接套用包含全量升级、WARP 或普通模板覆盖的 `software.yml`。当前仓库不包含服务商安装脚本、真实 inventory、用户身份或租约凭据；本记录没有宣称它是一套可无参数复刻住宅网络的通用 playbook。

## 计量与性能

- 与现有核心相同的固定版本与补丁，先在新机网络命名空间运行隔离校准；11 项正确性检查通过。
- 原生及住宅线路分别完成实际 Reality 试点，出口地址、国家码、原生计数器和逐连接累计一致。
- **CPU 性能门槛未通过。** 不同成对测试的相对 CPU 时间增幅约 16%–22%，高于项目原设的 15%；响应、吞吐及额外内存指标通过。用户明确接受该主机的性能开销后才继续。保留失败结果及例外记录，不更改默认门槛，不把该例外用于其他机器。
- 逐连接分类仍独立于总账，两者不重复添加。正常停止前排空总账与分类队列，重启后计量、监控、租约和绑定恢复。

## 修正的仓库问题

首次启用访问日志时，root 执行 `xray run -test` 会尝试打开访问日志。如果文件尚不存在，它可能成为 root 所有的 `0600` 文件，随后以 Xray 用户启动的服务无法写入。

`files/kenxu_meter.py` 现在在校验前创建或修正日志文件所有者和模式；不截断现有内容，不替换正在使用的 inode，拒绝软链接、硬链接和特殊文件。既有队列、客户端、路由与计量方式不变。

## 复核证据

- Linux 上 28 项 Python 测试全部通过，包含校验前准备日志、保留内容及拒绝链接／特殊文件。Windows 执行时三项 POSIX 测试跳过，不能替代 Linux 结果。
- 使用真实固定 Xray 二进制，root 校验之后再以实际 Xray 账号校验，二者均能打开预先准备的私有日志，旧记录保留。
- 新主机只读复核：两类队列排空、SQLite 完整、观察计数守恒、API 与 Unix socket 私有，节点和监控服务运行。没有对其他生产主机运行批量覆盖或核心重启。
